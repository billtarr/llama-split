| L-027 | 11-09 | LLM | **`rpcmem_free` 方案实测：IOVA 确实能回收，但性能 0.5 t/s，被纯 CPU 完败（8.5×）**。① 实现（`GGML_HEXAGON_RPCMEM_FREE=1`，同一份 `layer-serial.patch`）：回收时不 `unmap` 而是 `relinquish()`——先把 buffer 内容备到 host 侧 `std::vector`、记录每个 tensor 在 buffer 内的 offset，再 `mem.reset()` 走 `rpcmem_free` 销毁 dma_buf；下次用到时 `restore()`——重新 `rpcmem_alloc`、拷回、按 offset 重指所有 `tensor->data`、再 map。② **IOVA 真的回来了**：gemma4-e4b-q8_0（NPU 侧约 4.5 GB）在之前 `unmap` 方案下 **cum 卡死 2668.4 MiB**，换 `relinquish` 后 **cum 稳定在 4056 MiB 不再增长，模型能完整推理**（不再 `fastrpc_mmap` 0x1）。这条证实了 `qualcomm/fastrpc#137` 的「只有销毁 dma_buf 才还 VA」。③ **但代价是灾难性的**：`tg8 = 0.48 t/s`（预算 1536 MiB）/ **0.50 t/s**（预算 2048 MiB）；8 个 token 里 **copy 73~74 GiB**，即 **≈9.2 GB/token**（约 2× 模型大小），`relinquish` 164 次耗时 12.3 s、`restore` 153 次 5.9 s，实测搬运带宽仅 **~4 GB/s**。对照纯 CPU Q8_0 **4.26 t/s** → **慢 8.5 倍**。④ 瓶颈是**抖动**不是预算：预算从 1536 加到 2048 MiB，copy 量几乎不变（73.8→73.4 GiB）——LRU 在同一批块间反复换入换出。即使做到理想层序置换（每 token 只搬 4.5−2.0=2.5 GB），按 4 GB/s 也要 625 ms → **约 1.6 t/s，仍不到 CPU 的 40%**。**结论：`rpcmem_free` 是唯一能让 v73 装下 >2 GB 权重的手段，但搬运算不过账，实用性为零。** ⑤ 附带：teardown 阶段 `ggml_hexagon_measure_max_vmem` 里 `GGML_ASSERT(sbuf && sbuf->mem)` 会崩（有 buffer 停在 relinquished 态），未修——因为方案本身已否 | 现行（技术可行 / 性能否决） | 实测 |
